# База данных PostgreSQL

Документ описывает, как устроено хранение данных сайта после подключения
PostgreSQL, что делать при авариях и почему сделано именно так.

---

## Коротко

База **не заменила** файл `data/store.json`, а встала рядом с ним вторым
слоем:

```
память процесса  →  data/store.json   (синхронно, всегда, как раньше)
                 →  PostgreSQL        (в фоне, догоняет память)
```

Из этого следует всё остальное поведение:

| Что случилось | Что видит посетитель | Что делать администратору |
|---|---|---|
| База не поднялась при старте | ничего, сайт работает | ничего, попытки идут сами |
| База упала на ходу | ничего, заявки принимаются | посмотреть, почему упал контейнер |
| База вернулась | ничего | ничего, данные долились сами |
| Базы нет вовсе (`DATABASE_URL` пуст) | ничего | ничего |
| Потерян том с `store.json` | ничего | ничего, сайт поднялся из базы |
| Потерян том с базой | ничего | ничего, база наполнилась из файла |
| Потеряно и то и другое | сайт на демо-данных | восстановить из `./backups` |

Последняя строка — единственный случай, требующий ручных действий.

---

## Зачем база, если и без неё работало

Три причины, по порядку важности.

**Вторая независимая копия.** `store.json` — один файл на одном томе.
Он переживает перезапуск контейнера и пересборку образа, но не переживает
потерю тома. Теперь копий две, на разных томах, и одна беда не забирает обе.

**Потолок роста.** Файл целиком лежит в оперативной памяти процесса и
целиком переписывается при каждом сохранении. На четырёх заявках это
бесплатно, на четырёх тысячах — уже нет. В базе заявки лежат строками, с
индексами по дате, статусу и телефону: под серверную пагинацию, фильтры и
поиск дублей (задача 4 из перечня доработок) фундамент уже есть.

**Точка подключения снаружи.** К базе можно прийти из psql, выгрузить в
Excel, отдать в 1С, посчитать отчёт — не трогая работающий сайт.

При этом переход обратимый: очистите `DATABASE_URL`, и всё работает ровно
как до подключения, без единой правки в коде.

## Что появилось в проекте

| Файл | Назначение |
|---|---|
| `server/db.js` | Весь слой базы: подключение, живучесть, фоновая сверка |
| `server/db-schema.sql` | Схема. Накатывается сама при каждом старте |
| `server/db-cli.js` | Ручные операции: `db:status`, `db:import`, `db:export` |
| `scripts/pg-backup-loop.sh` | Ежесуточный `pg_dump` в `./backups` |
| `scripts/pg-restore.sh` | Восстановление базы из дампа |

Изменены: `server/store.js` (одна строчка отметки в `save()` и мост к слою
базы), `server/index.js` (запуск слоя, состояние в `/api/health`, два
админских эндпоинта), `server/notify.js` (сообщения о базе в Telegram),
`docker-compose.yml`, `.env.example`, `package.json`.

**Ни один из эндпоинтов API не переписан.** Это стало возможно потому, что
`store.js` изначально был спроектирован как единственный шов между API и
данными — в его комментариях этот переход прямо предусмотрен.

## Как данные попадают в базу

Не по одному запросу на каждую правку. Раз в `DB_SYNC_MS` (по умолчанию 3 с)
идёт **сверка**: для каждой записи считается отпечаток содержимого и
сравнивается с отпечатком, отправленным в прошлый раз. В базу уезжает только
изменившееся; исчезнувшее из памяти — удаляется. Всё внутри одной
транзакции: либо база догнала память целиком, либо осталась как была.

Так сделано по двум причинам. Первая: не пришлось трогать ни один из двух
десятков методов `store.js` — сверка сама видит, что поменялось. Вторая:
при обрыве связи не нужен журнал недоставленного. Память **и есть** полный
журнал, после переподключения сверка просто идёт целиком.

**Заявки — исключение.** Они уезжают в базу немедленно, не дожидаясь
очередной сверки: потерять обращение клиента в трёхсекундном окне
недопустимо, а всё остальное подождёт.

## Схема

В каждой таблице есть колонка `data` типа `jsonb` — это полная запись ровно
в том виде, в каком она лежит в `store.json`. Она источник истины. Колонки
рядом (`cat`, `status`, `sort`, `phone`…) — производные, их заполняет сервер
при записи; нужны для индексов и для чтения человеком из psql.

Разложить запись по колонкам полностью означало бы переписать все методы
`store.js` и получить **разную форму данных** в файле и в базе. Тогда откат
на файл перестал бы быть безопасным — а он должен работать всегда. Здесь
формат один, и любую из двух копий можно взять как есть.

Полезные запросы:

```sql
select id, date, status, type, fio, phone from requests order by created_at desc limit 20;
select phone, count(*) from requests group by phone having count(*) > 1;   -- дубли
select cat, count(*) from models where published group by cat;
select * from store_meta;                                                   -- когда была сверка
```

## Первый запуск на сервере

Сайт уже работает, у заказчика в `store.json` накоплен каталог и заявки.
Порядок такой, чтобы ничего из этого не потерять.

```bash
# 1. Снять копию ДО всего остального. Это единственный необратимый момент.
docker compose exec web cat /data/store.json > store-before-pg-$(date +%F).json
ls -la store-before-pg-*.json     # убедиться, что файл не пустой

# 2. Задать пароль базы в .env
echo "POSTGRES_PASSWORD=$(openssl rand -base64 24)" >> .env

# 3. Поднять базу отдельно и дождаться готовности
docker compose up -d postgres
docker compose ps postgres        # ждём healthy, первый запуск ~30–60 с

# 4. Пересобрать и запустить сайт
docker compose up -d --build web

# 5. Проверить, что перенос прошёл
docker compose logs web | grep -A2 "База данных"
```

В логе должно быть:

```
  База данных: подключаюсь к PostgreSQL…
  Источник данных: store.json (база пуста — первичный перенос данных из файла)
✓ Полная сверка с PostgreSQL: 52 записей, удалено 0, 31 мс
```

Проверка глазами:

```bash
docker compose exec postgres psql -U shmagro -d shmagro \
  -c "select 'моделей', count(*) from models
      union all select 'заявок', count(*) from requests
      union all select 'новостей', count(*) from news;"
```

Числа должны совпасть с тем, что показывает админка. Если совпали — перенос
состоялся, `store.json` при этом остался на месте и продолжает писаться.

Наконец, поднять бэкапы базы:

```bash
docker compose up -d db-backup
docker compose logs db-backup     # первая копия делается сразу
```

## Разбор аварий

### Упал контейнер с базой

Ничего делать не нужно — сайт работает. Убедиться в этом:

```bash
curl -s https://shmagro.kz/api/health
# {"ok":true,"uptime":12345,"db":"down"}   ← ok:true, сайт здоров
```

`ok: true` при `db: down` — это не ошибка, а как задумано. Состояние базы
попадает в `/api/health` **справочно** и на код ответа не влияет: иначе
Docker перезапускал бы сайт каждый раз, когда база перезагружается.

Найти причину:

```bash
docker compose logs --tail 50 postgres
docker compose ps
free -m                 # чаще всего это нехватка памяти
```

Поднять обратно:

```bash
docker compose up -d postgres
docker compose logs web | tail -5
# ✓ PostgreSQL снова доступен (простой ~47 с). Доливаю данные из памяти…
```

Данные, накопленные за простой, долились сами.

### Потерян том с `store.json`, база цела

Сайт стартует, видит, что файла нет, поднимается **из базы** и пересоздаёт
файл. В логе:

```
  Источник данных: PostgreSQL (файла данных не было — поднимаемся из базы)
  ✓ подняли из базы: моделей 6, новостей 3, заявок 84
```

Ручных действий не требуется.

### Потерян том с базой, файл цел

Сайт видит пустую базу и переносит в неё содержимое файла — то же, что при
первом запуске. Ручных действий не требуется.

### Потеряно и то и другое

Единственный случай, где нужны руки. Копии лежат в `./backups`: `store-*` от
сервиса `backup` и `pg-*.dump` от `db-backup`.

Проще и быстрее — из копии файла:

```bash
docker compose stop web
docker compose run --rm restore
docker compose start web
```

Сайт поднимется из файла и сам наполнит пустую базу.

Из дампа базы (когда копия файла старше или отсутствует):

```bash
docker compose stop web
docker compose up -d postgres
docker compose run --rm pg-restore

# ВАЖНО: поднять сайт с DB_SOURCE=db, иначе он затрёт восстановленную базу
# своим старым файлом
DB_SOURCE=db docker compose up -d web

# проверить админку глазами, затем вернуть обычный режим
docker compose up -d web
```

### База и сайт разошлись

Кнопка **«Перелить заново»** в админке (или `POST /api/admin/db/resync`)
приводит базу к тому, что сайт показывает сейчас. Безопасна в любой момент:
ничего не удаляет ни из памяти, ни из файла.

## Ручные операции

Рассчитаны на **остановленный** сайт: живой сайт держит данные в памяти и
перезапишет `store.json` своей копией, если тронуть файл у него под руками.

```bash
# что в базе
docker compose exec web node server/db-cli.js status

# файл → база (принудительно, поверх содержимого базы)
docker compose stop web
docker compose run --rm --entrypoint "" web node server/db-cli.js import
docker compose start web

# база → файл (прежний файл сохраняется рядом с меткой времени)
docker compose stop web
docker compose run --rm --entrypoint "" web node server/db-cli.js export
docker compose start web
```

## Что проверено испытаниями

Все сценарии прогнаны на живой базе, а не рассуждением.

| Сценарий | Результат |
|---|---|
| Первичный перенос `store.json` → база | 52 записи, 31 мс |
| Остановка базы `-m immediate` под потоком заявок | 72 заявки, **0 потерь**, процесс жив |
| Возврат базы | автоподключение, полная доливка, файл и база сошлись до записи |
| Старт при недоступной базе | старт за 12 мс, сайт работает |
| `DATABASE_URL` пуст | режим `off`, заявки принимаются |
| Потеря тома с файлом | поднялись из базы, 84 заявки на месте |
| Удаление и правка записей | база сходится с памятью, удалённое удалено |
| Падение базы под HTTP-трафиком | `/api/health` — `ok:true`, каталог и главная — 200 |
| `SIGTERM` при мёртвой базе | завершение за 217 мс (лимит Docker — 20 000 мс) |
| `pg_dump` → снос таблиц → `pg_restore` | данные вернулись полностью |

### Найденная и исправленная ошибка

Первый же прогон падения базы **убил процесс сайта**. Причина: обработчик
`pool.on('error')` ловит ошибки только на простаивающих соединениях. То,
которое выдано наружу через `pool.connect()`, при обрыве отправляет событие
`error` на себе, и Node превращает такое событие без слушателя в падение
процесса.

То есть падение контейнера с базой роняло бы сайт — ровно то, чего весь этот
слой должен избегать. Исправлено обёрткой `withClient()` в `server/db.js`;
сломавшееся соединение к тому же возвращается в пул с флагом уничтожения,
иначе оно ушло бы в оборот и следующая операция упала бы на нём уже без
внятной причины в логе.

Замечание на будущее: без реального теста с остановкой базы эта ошибка
дошла бы до прода и проявилась бы первым же перезапуском PostgreSQL.
